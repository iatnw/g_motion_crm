================================================================================
  G MOTION CRM — PROJECT NOTES & DOCUMENTATION
================================================================================

PURPOSE
-------
G Motion CRM is a single-owner CRM tool for an automotive financing broker.
The owner uses it to manage their clients, track financing deals, coordinate
with brokers and dealers, store documents, and monitor commissions and payments.
There is no multi-user support — the app has one authenticated owner.


================================================================================
  TECH STACK
================================================================================

Backend:
  - Language:    Go 1.26.1
  - Router:      Chi v5 (lightweight HTTP router with middleware support)
  - Database:    PostgreSQL 16
  - Queries:     sqlc v1.30.0 (SQL-first, generates type-safe Go from .sql files)
  - Migrations:  Goose v3 (runs automatically on server startup)
  - Auth:        JWT (golang-jwt/jwt v5) + TOTP (pquerna/otp)
  - Passwords:   bcrypt (golang.org/x/crypto)
  - Hot-reload:  Air (watches *.go, rebuilds to ./tmp/main)

Frontend:
  - Framework:   Next.js 16.2.1 with App Router
  - Language:    TypeScript 5
  - Styling:     Tailwind CSS 4
  - Node:        20

Infrastructure:
  - Docker Compose (postgres + backend + frontend services)
  - PostgreSQL 16 Alpine with health checks
  - .env file for all environment configuration

================================================================================
  SERVER ENTRY POINT
================================================================================

File: backend/cmd/server/main.go

--- STARTUP SEQUENCE ---

1. config.Load()
   Reads .env (only if APP_ENV not set in environment), validates required vars.
   Fails fast if DATABASE_URL, APP_PORT or JWT_SECRET are missing.

2. pgxpool.New()
   Opens a PostgreSQL connection pool. The pool manages multiple concurrent
   connections. stdlib.OpenDBFromPool wraps it into a *sql.DB for Goose and sqlc.

3. goose.Up(sqlDB, "migrations")
   Runs all pending migrations from the migrations/ folder on every startup.
   Guarantees the DB schema is always up to date when the server starts.

4. Dependency wiring — in strict order:
     db.New(sqlDB)             → queries       (sqlc layer, talks to DB)
     service.NewAuth(queries)  → authService
     service.NewBroker(queries)→ brokerService
     service.NewDeal(queries)  → dealService
     service.NewClient(queries)→ clientService
     handler.New*(service)     → handlers      (HTTP layer, talks to services)

   Each layer only knows about the layer directly below it.
   Handlers never touch the DB. Services never touch HTTP.

5. Chi router setup
   Global middleware applied to all routes:
     chimiddleware.Logger    — logs every incoming request
     chimiddleware.Recoverer — catches panics, returns 500 instead of crashing

6. Route registration — three access tiers:

   Public (no token required):
     GET  /health           — liveness check
     POST /auth/login       — password login

   totp_pending group (middleware.Auth with stage "totp_pending"):
     POST /auth/totp/verify — completes 2FA login, issues authenticated token
     Only accepts the short-lived totp_pending JWT issued after password login.

   authenticated group (middleware.Auth with stage "authenticated"):
     All auth management routes (totp setup/enable/disable, password)
     All CRUD routes: /clients, /brokers, /deals

7. http.ListenAndServe on APP_PORT — fatal if it fails to bind.


================================================================================
  AUTHENTICATION
================================================================================

Files:
  backend/internal/service/auth.go    — business logic
  backend/internal/handler/auth.go    — HTTP layer
  backend/internal/middleware/auth.go — request guard

The app has one owner account. No registration flow — the owner account is
seeded via CreateSetting with an initial bcrypt-hashed password.

--- JWT Token Stages ---
Tokens carry a custom "stage" claim. The middleware enforces that only
"authenticated" stage tokens can access protected routes.

  "totp_pending"   — issued after correct password when TOTP is enabled
                     TTL: 5 minutes. Can only be used with /auth/totp/verify.
  "authenticated"  — issued after full login (no TOTP) or after TOTP verify
                     TTL: 24 hours. Required for all protected endpoints.

Signing: HMAC-SHA256 using JWT_SECRET.

--- Login Flow (no TOTP) ---
  POST /auth/login  { "password": "..." }
  → validates password against bcrypt hash in settings
  → returns { "token": "<authenticated JWT>", "totp_required": false }

--- Login Flow (TOTP enabled) ---
  POST /auth/login  { "password": "..." }
  → validates password
  → returns { "token": "<totp_pending JWT>", "totp_required": true }

  POST /auth/totp/verify  { "code": "123456" }
  → validates TOTP code against stored secret
  → returns { "token": "<authenticated JWT>" }

--- TOTP Setup Flow ---
  POST /auth/totp/setup   (requires: authenticated token, TOTP not yet enabled)
  → generates new TOTP secret via pquerna/otp
  → returns { "secret": "BASE32SECRET", "key_uri": "otpauth://..." }
  → secret is NOT yet saved — owner must confirm with a code first

  POST /auth/totp/enable  { "secret": "...", "code": "..." }
  → validates the TOTP code against the provided secret
  → if valid, saves secret to settings (enables TOTP for future logins)
  → returns 204 No Content

  POST /auth/totp/disable (requires: authenticated token)
  → sets owner_totp_secret to NULL in settings
  → returns 204 No Content

--- Password Change ---
  POST /auth/password  { "password": "newpassword" }   (requires: authenticated)
  → bcrypt-hashes the new password
  → updates settings.owner_password_hash
  → returns 204 No Content

--- Auth Middleware ---
  File: backend/internal/middleware/auth.go
  - Reads Authorization header, expects "Bearer <token>"
  - Calls AuthService.ParseToken to validate and decode JWT
  - Rejects if stage != "authenticated"
  - Stores *Claims in request context under key "claims"
  - GetClaims(ctx) helper retrieves claims from context in handlers


================================================================================
  HANDLER LAYER — BROKER & DEAL
================================================================================

Files:
  backend/internal/handler/broker.go
  backend/internal/handler/deal.go

--- GENERAL FLOW (applies to all handlers) ---

Every handler follows this sequence:
  1. Parse inputs (URL params, request body)
  2. Validate required fields
  3. Call service method
  4. Handle errors (404 vs 500)
  5. Write JSON response

--- REQUEST TYPES ---

Optional fields use *string in request structs. This distinguishes between
a field being absent (nil → NULL in DB) and an empty string ("" → stored as-is).
Required fields use plain string.

  brokerRequest  — first_name, last_name required; phone, email, notes optional
  dealRequest    — client_id required; all other fields optional

--- UUID HANDLING ---

Two helper functions in the handler package:

  nullUUID(s *string) (uuid.NullUUID, error)
    — nil input    → uuid.NullUUID{Valid: false}  (stored as NULL)
    — valid string → uuid.NullUUID{UUID: parsed, Valid: true}
    — invalid UUID → returns error → handler responds 400

  nullString(s *string) sql.NullString   (defined in broker.go, shared across package)
    — nil input    → sql.NullString{Valid: false}
    — non-nil      → sql.NullString{String: *s, Valid: true}

--- DATE HANDLING ---

  nullTime(s *string) (sql.NullTime, error)
    — nil input            → sql.NullTime{Valid: false}
    — "YYYY-MM-DD" string  → sql.NullTime{Time: parsed, Valid: true}
    — wrong format         → returns error → handler responds 400

  dateLayout const = "2006-01-02"
    Go's time.Parse uses a reference time to define format, not placeholders.
    The reference year is 2006 — using any other year silently breaks parsing.

--- ENUM HANDLING ---

Enum fields arrive as plain strings and are cast to their db types:
  nullDownPaymentMethod(*string) db.NullDownPaymentMethod
  nullPaymentStatus(*string)     db.NullPaymentStatus
  nullReferralStatus(*string)    db.NullReferralStatus

No validation of enum values at the handler level — invalid values will
cause a DB error which surfaces as 500. Enum validation can be added later.

--- ERROR RESPONSES ---

  sql.ErrNoRows  → 404 Not Found   (get/update on non-existent record)
  any other err  → 500 Internal Server Error

--- STATUS UPDATE ENDPOINTS ---

UpdateBrokerFeeStatus, UpdateBrokerCommissionStatus, UpdateReferralStatus
all follow the same minimal pattern:
  Body: { "status": "paid" | "not_paid" }   (referral also accepts "none")
  The paid_date column is automatically set/cleared by the SQL query itself
  (CASE WHEN status = 'paid' THEN CURRENT_DATE ELSE NULL END)
  so no date handling is needed in the handler or service.

--- LIST WITH FILTER ---

GET /deals accepts optional ?client_id= query param.
  - If present and valid UUID → calls ListByClient
  - If present and invalid UUID → 400
  - If absent → calls List (returns all deals)

================================================================================
  SSN ENCRYPTION
================================================================================

Files:
  backend/internal/service/crypto.go    — encrypt / decrypt helpers
  backend/internal/service/client.go    — encryption wired into client service
  backend/internal/config/config.go     — ENCRYPTION_KEY loaded from env
  backend/cmd/server/main.go            — key decoded and passed to NewClient

SSN is sensitive PII. It is encrypted at rest using AES-256-GCM (field-level
encryption). The raw SSN string never touches the database.

--- How it works ---

  encrypt(key, plaintext) → base64 string
    1. Creates AES-256 cipher block from the 32-byte key
    2. Wraps it in GCM mode (authenticated encryption — detects tampering)
    3. Generates a fresh random 12-byte nonce for every call
    4. Seals the plaintext: output = nonce + ciphertext + auth tag
    5. Base64-encodes the whole thing → safe for TEXT column storage

  decrypt(key, base64string) → plaintext string
    1. Base64-decodes the stored value
    2. Splits off the first 12 bytes as the nonce
    3. Opens (decrypts + verifies auth tag) the remaining bytes
    4. Returns the original plaintext SSN

  A new nonce is generated on every encrypt call, so two encryptions of the
  same SSN produce different ciphertext. This is correct and expected behavior.

--- Service layer integration ---

  ClientService holds encryptionKey []byte (32 bytes, passed at construction).

  Create — if Ssn is present, encrypt before writing to DB
  Update — if Ssn is present, encrypt before writing to DB
  Get    — if Ssn is present in DB row, decrypt before returning
  List   — decrypt SSN on every row before returning

  The decryptSSN helper handles the NULL case — if SSN is not set, it's a no-op.
  Callers always receive plaintext SSN. Encryption is fully internal to the service.

--- Key management ---

  ENCRYPTION_KEY in .env must be a 64-character hex string (32 bytes).
  Generate a key:
    openssl rand -hex 32

  On startup main.go decodes the hex string and validates it is exactly 32 bytes.
  Server refuses to start if the key is missing, invalid hex, or wrong length.

--- Limitations / future ---

  - Key rotation is not yet implemented. To rotate: re-encrypt all SSN values
    in a migration using the old key → re-encrypt with new key → update env.
  - No search on SSN (encrypted values are not queryable). Lookup is by id/phone.
